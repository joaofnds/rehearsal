# Proposals from the Promptfoo study

These are recommendations, **not accepted roadmap changes**. The
[study synthesis](../promptfoo-study.md) gives the comparison and proposed vision
revisions; [architecture](architecture.md) and [evidence](evidence.md) support the
claims below. Effort is relative scope, not a delivery estimate: small means an
existing projection or document boundary, medium spans records and commands,
and large adds an execution or product boundary.

## Recommended sequence

| Order | Proposal                                 | Expected value / evidence                                                            | Effort / fit                         | Disposition and dependency                                    |
| ----- | ---------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------ | ------------------------------------------------------------- |
| 1     | P1: realistic session loop               | High: current checks cannot establish produced-code correctness; explicit public gap | Medium–large / core                  | Complete accepted work; deliver one public end-to-end example |
| 1     | P2: defensible claims                    | High: implemented formulas and tested comparison boundaries expose limits            | Medium / core                        | Extend comparisons; initial claim labels need not wait for P1 |
| 1     | P3: bounded execution                    | High: unbounded rep launch is code-established; contention magnitude unknown         | Medium; sandbox later large / core   | Shape concurrency and cancellation first; run fault probes    |
| 2     | P4: evidence-led instruction experiments | High: accepted inspector and attribution work; demand for combined flow inferred     | Medium across existing slices / core | Extend existing context roadmap after usable outcome evidence |
| 3     | P5: portable regression reports          | Medium: Promptfoo demonstrates CLI gating/export; team demand unverified             | Small–medium / strong                | Read-only report first; paid CI execution after P2/P3         |
| Later | P6: second runtime and isolated runners  | Potentially high reach; benefits and parity unverified                               | Large / conditional                  | Bounded adapter/fidelity investigation before commitment      |

The order favors trustworthy outcomes and operability over provider count or
screen count. P1–P4 share prerequisites and should reuse existing work. This
table does not reprioritize the maintainer board. Investigations may be shaped
from it; implementation is a separate decision.

## P1: Complete the realistic session loop

**User problem.** An engineer sees an agent read the right instruction and call
a test command, but cannot tell whether it produced correct code. The smallest
Rehearse cases grade reply/tool evidence and discard the final working directory.
That limits both first use and cheap instruction experiments.

**Evidence and current position.** Promptfoo combines extensible assertions with
provider metadata and encourages artifact verification in its
[coding-agent guide][p-agent-guide]. Rehearse already has fixtures, deterministic
session checks, retained transcripts, pipeline integrity checks, and checkpoint
replay. Its [current limits](../status.md#known-limitations) and
[accepted session work](../context-visibility.md#accepted-roadmap) explicitly
cover frozen skills, generated fixtures, retained filesystem/Git state, richer
scoring, and regrading. This proposal extends that work; it does not introduce a
second evaluator.

**Adaptation: product and architectural inspiration.** Make a public coding case
exercise the complete sequence: materialize a frozen fixture and isolated
instruction variant, execute the real agent, preserve the final artifact and
diff, run bounded command/file checks outside agent control, retain stdout,
stderr and exit status, inspect a failure, regrade saved evidence, and confirm a
candidate against baseline and minimal control. A generated fixture is an
experimental input: record its generator/version/seed and generated bytes.
Protect grader inputs and verifier hashes from candidate modification.

Start with one narrowly specified behavior, such as adding a feature without
weakening existing tests. Include two or more task variants for the current
comparison contract. A read-only provider-free example should let a new user
inspect known good, bad, and missing evidence before paying for an agent run.
Treat onboarding packaging as part of finishing the accepted loop.

**Benefit.** Short session experiments can establish useful coding outcomes;
engineers can debug grader changes without paying to regenerate artifacts.

**Costs, risks, dependencies.** Artifact retention increases storage and privacy
exposure. Scorers execute code and need time/output limits, controlled inputs,
and a defined environment. Regrading changes the measurement contract and must
produce a new grade record linked to the unchanged attempt, never silently
rewrite historical success. Depends on isolated skill delivery, artifact
capture, record compatibility, and P3's execution policy for stronger isolation.
Avoid importing Promptfoo's entire assertion catalog until cases demand it.

**Validation.** A clean clone can inspect the provider-free case, then run its
paid recipe with a stated ceiling. Seed defects that produce plausible replies
and test invocations while leaving broken code or edited verifiers; the artifact
grade must catch them. Regrading must make zero provider calls and preserve the
original evidence and grade. Compare the original and changed instruction on
fixed criteria; usability success is a second engineer completing this loop
without maintainer-only files. Paid validation remains outstanding.

## P2: Make the supported claim part of the comparison

**User problem.** A small experiment appears conclusive, or lower observed cost
gets described as quality preserved. The engineer needs to know which decision
the evidence can support before accepting an instruction change.

**Evidence and current position.** Promptfoo provides repetitions, component
scores and gates, but the inspected core does not enforce causal comparisons.
Rehearse is stronger here: it validates inputs, retains failures, computes
within-case arm means, and estimates the mean/standard error of paired case
differences. Yet its reliability report uses `sqrt(p*(1-p)/n)` and
`passK = p ** requested`. At 5/5 successes those readings are `0` and `1`.
They are plug-in estimates, not certainty about future success. Case-delta SE
also collapses within-case sampling variation into arm means. Two cases with
identical deltas can produce SE zero despite uncertain individual outcomes.
[Estimator][r-estimate], [reliability report][r-reliability],
[existing research](../research.md#report-uncertainty-and-pair-comparisons-by-case).

**Adaptation: independent methodological proposal prompted by the comparison.**
Add a declared claim to an experiment: narrow behavior reproduction, suite-level
quality improvement, quality-preserving efficiency, or regression detection.
Record target task population, chosen quality endpoints, minimum useful effect
or tolerated quality loss, repeat plan, stopping rule, and discovery versus
confirmation case membership before examining confirmation results.

Prespecify arm order or counterbalanced/interleaved scheduling when feasible,
and record timing, provider rate-limit incidents and cache conditions. Repeating
arms at different times can confound an instruction effect with provider or host
changes. Record dependence from reused sessions or shared services rather than
assuming repetitions are independent. Keep model-side prompt-cache usage
separate from replay of a whole cached answer.

Retain the existing estimates as descriptive readings. Shape interval methods
for small binary samples and nested case/repetition variation; do not relabel a
standard error as a confidence interval. Keep the displayed number of cases
separate from repetitions. Expose `k` and distinguish the current plug-in
`passK` calculation from independently observed repeated-success evidence.
Require a fixed `k` for comparable reliability claims. The exact estimator and
acceptance thresholds remain investigation outcomes, not settled by this study.

Provide explicit verdicts for comparable evidence: improvement supported,
regression supported, and inconclusive. Keep invalid/incomparable evidence a
separate state. For quality-preserving savings, use a prespecified quality
noninferiority criterion together with cost change; failure to detect a quality
loss is insufficient. Split execution reliability, gradeability, and judged
quality so missing metrics remain visible without being mistaken for a code
defect. Report all attempted costs and the missing-cost count.

Treat the minimal-corpus arm as a calibration/control question, while the
candidate–baseline contrast answers whether the edit helped. “Minimal” must be
defined per case: required task facts and harness safety constraints cannot
silently disappear. Discovery retries and changed graders require new lineage;
selected winners need reserved confirmation cases. Broader model/effort changes
are separate experimental conditions, not confounders to average away.

**Benefit.** A report can support a decision without overstating a small sample.
The result may legitimately be “run more varied cases” or “keep the baseline.”

**Costs, risks, dependencies.** More rigorous confirmation costs money and may
return inconclusive results frequently. Tiny hand-picked suites cannot justify
population claims even with sophisticated intervals. Sequential stopping,
multiple endpoints, and optimizer search add selection bias unless specified.
Extends existing comparison explanations and the accepted efficiency benchmark;
requires no general statistics framework in the first slice.

**Validation.** Test all-pass/all-fail small samples, identical case deltas,
unequal variability, missing grades and metrics, and changed input contracts.
Run synthetic null/effect simulations to assess coverage and false decisions
under the chosen assumptions, then a bounded real-provider repeat study. A
report must never equate an observed SE of zero with certainty. An engineer
should identify the claim, denominator, uncertainty, control role, and next
experiment from the report alone. Consult the primary
[error-bar methodology](https://arxiv.org/abs/2411.00640v1) when shaping; the paper
does not certify Rehearse's current formulas.

## P3: Bound execution and record the environment

**User problem.** Repetitions contend for local/provider resources, an abort
leaves uncertain state, or a worktree is described as more isolated than it is.
The operator cannot plan the experiment or distinguish instruction effects
from environmental drift.

**Evidence and current position.** Rehearse's confirmation helper launches all
rep plans with `Promise.all`. It already has detached process-group timeouts,
per-session dollar budgets, projected confirmation ceilings, pipeline abort
handling, and separate repetition worktrees. These are valuable foundations;
there is no aggregate CPU/memory/disk/network policy in those inspected paths.
[Confirmation][r-confirm], [commands][r-command], [abort lifecycle][r-abort].
Promptfoo's Codex adapters illustrate same-thread serialization, explicit
runtime policies and cancellation propagation. They do not replace experiment
workspace preparation. [Agent comparison](architecture.md#running-coding-agents).

**Adaptation: architectural inspiration.** Add configurable bounded concurrency
with durable queued/running/finished/cancelled/not-started states and a shared
cancellation signal. Record the concurrency policy as an experimental condition.
Keep retries as linked new attempts, with original failures and spend retained.
Persist a run manifest describing the agent/runtime version, resolved model and
effort when observable, OS/toolchain, starting commit and dirty state, fixture,
corpus, project instructions, grader inputs, permissions, session reuse, allowed
integrations, and external-state assumptions. Record secret names or scopes,
not values.

Distinguish planned spend ceilings, observed spend, enforcement mechanisms, and
unknown in-flight cost. A budget policy should stop dispatching new work and
cancel work where supported; it cannot promise zero overshoot from delayed
usage. Record which limits the provider enforces and which Rehearse enforces.
For now, define a reproducibility boundary for host runs and name residual
mutable inputs. Investigate a container/VM profile separately under P6.

**Benefit.** Predictable local load, recoverable cancellation, and better grounds
for explaining incomparable results. Environmental evidence also makes bugs
reproducible for a second maintainer.

**Costs, risks, dependencies.** A scheduler adds shutdown and persistence races.
Serial execution may be slower; concurrency changes timing and rate limits.
Manifest schemas need backward-compatible unknown states. An exhaustive host
snapshot is impractical and may leak private paths. Integrate with existing
restoration, provider metrics and record versioning, rather than invent a
parallel job system.

**Validation.** Fault-inject abort while queued, during a subprocess, during
record writing, and during cleanup; also test timeout, disk-write failure and
provider rate limits. Verify no undisclosed attempt disappears, all started
costs remain attributable or explicitly missing, and cleanup receipts describe
residue. Compare concurrency 1 and a bounded parallel setting on the same
fixtures to measure contention. A process crash test must be separate from a
cooperative abort test. Real provider descendant-process cleanup remains to be
verified.

## P4: Connect observed failures to instruction hypotheses

**User problem.** An engineer can see an expensive trajectory but cannot easily
turn that observation into a reproducible edit and a defensible comparison.
A repeated read or large tool output can suggest waste without proving it.

**Evidence and current position.** Promptfoo links cell results to prompts,
grades, metadata and traces; its optimizer uses bounded failure examples to
propose changes. Rehearse already serves saved session context, request token
and cost timelines, source locators, and comparison links. Its accepted roadmap
covers a unified attempt index, integrations, artifacts, diagnostics, bounded
queries, MCP, reviewer trees and efficiency comparisons. Those are the home for
this proposal. [Inspector][p-inspector], [optimizer][p-optimize],
[accepted integration work](../context-visibility.md#integration-and-artifact-investigation).

**Adaptation: product inspiration.** Add a small experiment record linking the
observed failure and evidence locator, suspected instruction block, alternative
explanations, candidate corpus diff, predicted outcome, frozen case/grade
contract, and confirmation groups. Keep the edit in the user's existing editor;
an in-app corpus editor is not a prerequisite. One failure can seed a test,
while held-out task variants check whether the edit generalizes.

Use the shared saved-evidence projections across UI/CLI/read-only agent tools.
A diagnostic opens the source observation, then a candidate experiment, then
its outcome distributions. Group direct and descendant requests by stable
identity; expose reported, calculated, estimated and unallocated cost separately.
Retain images/offloads with the distinction between saved artifact and the
excerpt delivered to the model. Protocol events and OTEL spans are optional
inputs to this model, not a second authoritative ledger.

**Benefit.** Inspection ends in a falsifiable change, and engineers can explain
why they kept, revised, or removed an instruction.

**Costs, risks, dependencies.** More links and metadata can burden authoring.
Heuristic diagnostics can bias engineers toward deleting useful instructions.
Attribution cannot identify marginal causal cost without controlled reruns.
Depends on P1/P2 and accepted pipeline/child collection; initially support saved
sessions only and expose collection gaps.

**Validation.** Use the already accepted review-efficiency benchmark: preserve
its seeded-defect detection requirements, compare baseline/smaller variant/control,
and trace one diagnostic into a confirmed or rejected edit. Verify request IDs
prevent double counting, missing children remain unknown, and UI/CLI queries
agree. A second engineer must reconstruct the decision from saved records.
Reject any success criterion based solely on fewer tokens or a shorter rule.

## P5: Export portable regression evidence before adding CI execution

**User problem.** The engineer needs to review an instruction change with another
person or monitor model migrations without rerunning expensive work or sharing
private transcripts.

**Evidence and current position.** Promptfoo's JSON/JUnit outputs and exit gates
fit standard CI, while its in-place retry illustrates the risk of losing the
original error history. Rehearse has scriptable saved reports, staleness checks,
and an accepted content-free aggregate export, but pipeline progress can mix
with JSON stdout. [CI gate][p-gate], [retry][p-retry],
[current limits](../status.md#known-limitations).

**Adaptation: product inspiration.** First export a versioned comparison summary
containing input/grade identities, scope, denominators, per-case outcomes,
uncertainty, freshness and the P2 decision. Reuse the aggregate privacy boundary
already accepted. Offer JUnit as an index into the authoritative comparison
JSON, not the full measurement contract. Use distinct machine outcomes for
supported pass, supported regression, and invalid/inconclusive evidence; a
pipeline may choose to block on the last state without calling it regression.
Fix stdout/stderr discipline before documenting a new machine pipeline.

A later CI recipe should separate trusted scheduled/manual paid execution from
read-only PR report checks, with a pinned suite and explicit budget. Resolve
which baseline is approved and invalidate it when its experiment contract
changes. Never run repository-supplied scorers with privileged credentials just
because they arrive in a pull request.

**Benefit.** Reviewable evidence supports teams and migration decisions without
a hosted service or a permanent CI spending commitment.

**Costs, risks, dependencies.** Exports can disclose corpus content, paths,
identities or secrets. Binary CI pressure can hide inconclusive outcomes.
Depends on P2 verdicts, existing aggregate-export design and stable record
readers; execution also depends on P3. Team demand is still a hypothesis.

**Validation.** Open an export on a second machine with no private paths and no
provider calls; preserve unknown measurements and failed attempts. Round-trip
checks must match the saved report's values. Feed valid, stale, regression and
inconclusive fixtures through a consumer. Verify content-free export against
fixtures containing unique secret/path markers. Test whether two engineers can
review the same proposed change without explaining the run orally.

## P6: Investigate a second runtime and stronger isolation

**User problem.** Some engineers maintain Codex instructions, or need adversarial
fixtures that should not execute against their ordinary host environment.
Claude-only host execution limits those users; adding an adapter prematurely
could weaken the evidence contract.

**Evidence and current position.** Promptfoo's app-server implementation exposes
commands, file changes, requests, turn interrupts, and thread lifecycle beyond a
plain completion API. Rehearse uses a real Claude CLI and already normalizes
provider evidence, but live collection remains incomplete. The previous
[context-analyzer study](../context-analyzer-study.md) deferred a second provider
until a supported execution/import requirement exists. This proposal is a
reopening criterion and investigation, not a reversal of that decision.

**Adaptation: architectural inspiration; direct reuse only a candidate.** Run a
bounded Codex adapter spike on one frozen fixture using fresh threads. Compare
CLI fidelity, settings/instruction loading, artifacts, child evidence, request
usage and cancellation with a human-driven run. Keep Rehearse's checkpoint,
fixture, grading and comparison layers above the runtime. Define capability
flags and refusal behavior rather than fabricate cross-provider equivalence.
Separately test an isolated runner profile with controlled credentials, writable
paths, network and process limits; host execution can remain an explicit
fidelity profile.

**Benefit.** Evidence could justify serving another coding-agent community and
running stronger adversarial cases. A negative result can prevent an expensive
adapter commitment.

**Costs, risks, dependencies.** Large maintenance burden from protocol churn,
auth differences, provider usage semantics, platform support and sandbox/fidelity
tradeoffs. The SDK/app-server paths may behave differently from installed CLI
workflows. Requires P1/P3 contracts and real capture verification. Do not block
the current Claude outcome and collection work on this investigation.

**Validation / decision gate.** Produce a capability matrix and retained artifacts
for successful execution, cancellation, timeout, a denied action, a child agent,
and a repeated fresh run. Record unsupported evidence honestly. Advance only
if intended users need it and the adapter preserves Rehearse's minimum contract;
otherwise retain an observational import path or defer. No real-provider result
in this study establishes that gate.

## Ideas to defer or reject

| Idea                                                          | Decision and reason                                                                              | Evidence / reopening condition                                                                                                     |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Feature parity across models, RAG metrics and data connectors | Reject as an objective; it expands the job beyond instruction effectiveness                      | Promptfoo's broad provider/assertion model is documented; revisit a specific adapter only for a real user case                     |
| Replace Rehearse with Promptfoo as its execution engine       | Defer; would need frozen artifacts, comparison eligibility and attempt history layered around it | Provider and retry inspection; compare integration effort with a narrow adapter before choosing                                    |
| Generic weighted quality leaderboard                          | Reject for acceptance; blockers and missing evidence must remain visible                         | Executed threshold probe; allow exploratory named scores beside hard gates                                                         |
| Cache completed agent answers in confirmation                 | Reject as fresh behavioral evidence; permit clearly labeled offline inspection/regrading         | Executed repeat-cache tests; model-side prompt caching remains normal usage, distinct from whole-response replay                   |
| Broad red-team/compliance platform                            | Reject for current scope                                                                         | Adapt selected adversarial cases for instruction trust and verifier integrity; revisit only with an explicit new user/problem case |
| Autonomous instruction optimizer                              | Defer until the manual loop and holdout protocol work                                            | Optimizer uses validation for selection; independent final confirmation and search budgets are prerequisites                       |
| In-app instruction editor and full live monitor first         | Defer as dependencies of the first useful loop                                                   | Existing editor plus saved views suffice; follow accepted saved-before-live sequencing                                             |
| Generic OTEL backend or second metrics ledger                 | Defer; normalize optional spans into existing evidence                                           | Request identity, duplicate spans and cost reconciliation must be demonstrated first                                               |
| Hosted multi-user service, SSO and RBAC                       | Defer; team demand and operating model unvalidated                                               | Test portable report review first; local server is not an authorization boundary                                                   |
| Uncalibrated skill-use/waste scores                           | Reject as conclusions                                                                            | Tool invocation, lexical reads, elapsed spans and total input tokens cannot establish compliance or savings                        |

## Licensing and reuse boundary

The pinned Promptfoo repository declares MIT licensing; its license requires
preserving the copyright and permission notice in copies or substantial portions.
Rehearse also has an MIT [license](../../LICENSE). This study copies no Promptfoo
implementation. Its probes are original minimal configs. [Pinned license][p-license].

The recommended near-term work is architectural/product inspiration and
independent implementation. P6 could justify extracting a small normalization
or cancellation pattern after dependency review. If code is copied, record its
source commit, retain the required notice, check the specific file and bundled
dependencies, and decide how security/SDK changes will be tracked. Taking the
entire adapter also takes logger, tracing, cache, configuration and runtime
couplings. Public enterprise documentation does not grant access or reuse rights
to proprietary service code, commercial features, or third-party SDK assets.

## Investigations before implementation commitments

| Uncertainty                             | Smallest useful investigation                                                          | Decision it resolves                                               |
| --------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Statistical claim quality               | P2 simulation over small binary/nested samples plus a prespecified real repeat study   | Interval method, sample/stopping guidance, acceptable wording      |
| Real coding outcome portability         | P1 clean-clone case with two engineers                                                 | Whether the first-use promise is achievable                        |
| Hidden environment and resource effects | P3 fault probes and serial/parallel comparison                                         | Manifest scope, default concurrency, cancellation guarantees       |
| Child context and dollars               | Existing capture probe expanded to child loss, duplicate events and mixed models       | Which attribution units may be called measured                     |
| Grader validity                         | Human-label preserved artifacts including subtle seeded defects, by exact rubric/model | Where deterministic checks suffice and where Judges may be trusted |
| Team demand                             | P5 report review trial before hosted product design                                    | Whether proposed audience expansion is useful                      |
| Codex/sandbox fidelity                  | P6 bounded protocol and host/isolated comparison                                       | Whether a larger runtime investment is warranted                   |

These investigations remain open. They do not prevent choosing the near-term
sequence, but they prevent promising numerical savings, calibrated confidence,
sandbox guarantees, live-provider parity, or a broader market fit today.
