### 1. ACT-30 is four tests wider than it says

The 2026-09-03 note recorded one fresh-clone failure. That measurement was
taken at `/tmp/act30probe`, a clone one level under `/tmp`, where
`../../../nest/template` resolves to `/nest/template`. Absent, so ACT-34's test
failed there. But the probe never saw ACT-30's own failures in a whole-suite
run, and concluded they were hidden by test ordering.

Re-measured 2026-09-04 at 45c522c on a clone placed where no `nest/` sibling
resolves (`/tmp/deep2/a/b/c/rehearsal`):

    mkdir -p /tmp/deep2/a/b/c
    git clone <repo> /tmp/deep2/a/b/c/rehearsal
    cd /tmp/deep2/a/b/c/rehearsal && bun install --frozen-lockfile
    bun test          # first run:  1021 pass, 5 fail
    bun test          # every run after: 1 fail

The first run of a clone fails five. Four are ACT-30's ENOENT:

- `loadComparisonEvidence > writes one read-only comparison report without external execution`
- `rehearsal > prints only the report path for a valid manifest, and nothing on stdout otherwise`
- `rehearsal > prints exactly the report JSON on stdout with --json`
- `rehearsal > delivers a record larger than the pipe buffer whole on stdout`

The fifth is ACT-34's. From the second run onward, four of the five are gone,
because an earlier test has created `.benchmark-runs`.

So the card understated its own blast radius: it names one test file, and three
of the four failures are in the CLI suite. The cost of leaving it is a new
contributor's first `bun test` failing five tests that all disappear on a
retry, which is the shape of defect that wastes the most time. Acceptance #2 is
rewritten to the whole-suite first run, which is what the defect actually is.

## Kaizen candidate

**A card's reproduction command must carry the conditions the failure needs, not
only the command.** Decision-1 made cards carry the command that produces a
number, and it worked: four counts were re-checked this run by running the
card's own command, and every one was settled without reconstructing anything.

But two cards this run failed a weaker test. ACT-34's reproduction is `bun test
src/benchmark/case.test.ts`, which passes on this machine and on a clone at the
wrong depth. ACT-30's was `bun test src/benchmark/comparison-loader.test.ts`,
which passes on a second run. In both cases the command is right and the
environment the command needs is missing, so a reader who runs it gets a green
result and concludes the card is stale.

Both cards were filed by sessions that had just watched the failure, in an
environment where it was reproducing, which is exactly the moment the condition
is invisible to the writer.

Quoted from the two cards, before this run's notes:

- ACT-34: "On any clone elsewhere it does not [exist]." It does, at most depths
  under `~/code`.
- ACT-30: "`bun test src/benchmark/comparison-loader.test.ts` run alone on a
  clone with no .benchmark-runs directory passes." Only on a clone's first run.

This is decision-1's own principle one level further out: a measurement is
reproducible when a stranger can get the same number, and the command is only
half of what they need. Proposed as question 3.
