## The finding of the run: the live corpus was broken and nothing said so

Measuring the file count above threw instead of returning a number.
SymlinkedEntryError, naming agents/escape.md.

~/.claude/agents/escape.md was a symlink to /tmp/stale-out-8nUK/secret.md, mtime
Sep 9 02:43. It was not chezmoi-managed and not tracked in the dotfiles git, both
checked before touching it. Removed this run under Ownership, after confirming it
was a probe artifact and not configuration.

Whose probe is NOT established, and an earlier draft of this doc said it was.
The name and the payload match ACT-130's reproduction fixture, which is why I
attributed it to that session. Review probed the script doc-52 actually records
and it cannot be the route: it plants the link under a `mktemp -d`, and its
`cp -RL` dereferences, so its agents/ is a real directory inside the temp tree.
I reproduced that: after `cp -RL`, `ls -ld $c/agents` shows a real directory, not
a link. A `cp -R` without -L WOULD write through, because ~/.claude/agents is
itself a symlink, but that is not the recorded script. So some probe from that
session planted it by a route nobody has identified.

What it broke, checked against the code rather than assumed. corpusReport against
the live source throws SymlinkedEntryError, and src/server/api.ts wraps
/api/corpus in no try/catch, so the corpus screen returned an error for the whole
window. captureStageCorpus throws on the same input. But `stale --corpus` does
NOT fail: staleness-report.ts catches SymlinkedEntryError and returns a named
refusal cause, which is precisely the degradation ACT-130 shipped. And
hashCorpusFiles walks only the declared layoutPaths, so a case not declaring
agents/escape.md was untouched. An earlier draft of this doc said "every
live-corpus hash failed" and named stale among the casualties; both were too
broad, and review caught them.

So the blast radius over roughly 02:43 to 10:40 is the corpus screen and the
directory-walking captures, not the whole harness.

Two things make this worth a card rather than a note. The defect recurs from a
shipped process, so the next reproduction fixture reintroduces it. And the
project's own checks structurally cannot see it: the file lives outside the
repository, in the operator's home tree, where git status and the suite have no
reach. doc-52's kaizen line already asks stages to clean up scratch probe files,
and that reflection did clean the two it could see in the repo root. It could
not see this one.

Filed as ACT-135, High, with the guard as the deliverable rather than the
deletion.

Worth noting for whoever builds it: ACT-130 exists to make one symlink degrade
instead of blanking a screen, and its own probe planted one in the live corpus.
ACT-130 fixed the run-history surface; corpusReport is a different surface and
still throws on this input.
